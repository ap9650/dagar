# Spec: Internationalisation (English + Hindi)

**Build slice:** Day 0 prompt 5 (setup), 1.6 (Hindi content), 3.4c (Hindi pass)
**Implements:** D16
**Depends on:** `next-intl` installed · migrations 0002 (i18n jsonb columns)
**Style:** `docs/HINDI_STYLE.md` — **load before writing any Hindi**

---

## 1. The two halves

Localisation in Saathi has two independent mechanisms. Confusing them is the main
source of bugs here.

| | UI strings | Curriculum content |
|---|---|---|
| Lives in | `messages/en.json`, `messages/hi.json` | `i18n` jsonb column on the row |
| Read via | `useTranslations()` / `getTranslations()` | `t(row, field, locale)` |
| Count | ~150 strings | 3 chapters × lessons + questions |
| Authored by | You, at build time | Claude Haiku, then verified by reading |

---

## 2. The load-bearing rule

> **`answer_value` is never translated.** `1/2` is `1/2` in every language.

Consequence: `lib/learning/grading.ts` has **no locale parameter and no import from
any i18n module.** A translation error can produce a confusing question; it must
never be able to mark a correct learner wrong. If a code path makes grading depend
on locale, that is a bug regardless of how it reads.

The `i18n` jsonb on `questions` covers `stem_md`, `solution_md` and `choices` labels
only. MCQ **choice ids** are language-independent too — translate the label, never
the id.

---

## 3. Resolution

```ts
t(row, field, locale)  →  row.i18n?.[locale]?.[field] ?? row[field]
```

English lives in the base columns and is **always** the fallback. A missing Hindi
translation renders English — never an empty string, never a blank screen.

Locale comes from a **cookie** (`saathi_locale`), read in `i18n/request.ts`.
`profiles.locale` is the durable record; the cookie is what every server render
actually reads. Never `navigator.language` — a shared phone's language is usually
the parent's, not the learner's.

**Not `localStorage`** (as this spec originally said). `localStorage` is invisible to
a Server Component, so a Hindi learner would get an English server render followed by
a flash to Hindi on hydration — on the language picker, of all screens. The cookie is
also the only carrier that works before a user row exists. Functional preference only:
no tracking, no consent gate.

The two stores are kept in step in `i18n/actions.ts`:

| Moment | What happens |
|---|---|
| Language picked at `/welcome` (signed out) | Cookie only. The profile does not exist yet |
| Profile created at `/onboarding/grade` | `profiles.locale` written from the cookie |
| Language changed in `/settings` | Cookie **and** `profiles.locale`, one action |
| Sign-in on a new device | `syncLocaleFromProfile()` — the profile wins |

Reading `profiles.locale` on every render was the alternative, and it puts a database
round-trip in front of every page for a value that changes about twice per learner.

## 4. Typography

Devanagari needs different metrics from Latin, and using the Latin scale makes Hindi
look cramped and hard to read.

| | Latin | Devanagari |
|---|---|---|
| Body | 17px / 1.6 | **18px / 1.75** |

Font: `Noto Sans Devanagari` for `hi`, `Inter` for `en`, both loaded on Day 0. Set
`lang` on `<html>` so the browser picks correct shaping and hyphenation.

**Hindi strings run 10–20% longer than English.** Every button and label must be
tested at the longer string — this is what slice 3.4c catches.

## 6. Acceptance criteria

**Mechanism**
- [ ] Every user-visible string comes from the message dictionary — a grep for hardcoded English in `components/` and `app/` returns nothing
- [ ] `t(row, field, locale)` returns English when the Hindi key is absent, for every localised table
- [ ] Setting `locale: "hi"` renders lesson bodies, question stems, solutions, UI chrome, tutor replies and the parent summary in Hindi — **for all three grades, with no English lesson text anywhere**
- [ ] `lib/learning/grading.ts` imports nothing from `next-intl` or any locale module
- [ ] Grading a Hindi-locale learner's answer produces byte-identical results to the same answer in English locale

**Content quality** (`HINDI_STYLE.md`)
- [ ] Lesson bodies and question stems read like the NCERT Class *N* Hindi textbook
- [ ] Maths terms are NCERT's — भिन्न, पूर्णांक, समीकरण — never transliterated English
- [ ] Numerals are Arabic (`1/2`), never Devanagari (`१/२`)
- [ ] KaTeX blocks are byte-identical between the English and Hindi versions of the same row
- [ ] Conversational surfaces use तुम for the learner, आप for the parent, with no mixing inside one string
- [ ] No Latin script mid-sentence anywhere in Hindi copy

**Rendering (slice 3.4c)**
- [ ] Every screen walked in Hindi at 360px width with no clipped or wrapped-to-two-lines buttons
- [ ] Devanagari renders at 18px/1.75, not the Latin 17px/1.6
- [ ] No screen shows a mix of English and Hindi except where English is a deliberate fallback

## 7. Edge cases

| Case | Required behaviour |
|---|---|
| **Hindi missing for a lesson** | Renders English. The learner sees content, not a blank. All three chapters ship with Hindi, so this is now a genuine safety net rather than an expected path — but it must still look intentional if it fires. |
| **English `body_md` edited, Hindi left stale** | The main ongoing risk. Nothing catches it automatically. Rule: change both in the same commit. Call it out in review. |
| **Tutor grounded in English while learner reads Hindi** | **The dangerous one.** The model translates on the fly, bypassing review, and can produce wrong maths. Pass the *resolved* locale body as grounding, and instruct the reply language explicitly. |
| **Learner switches language mid-lesson** | Re-render in place at the same lesson and scroll position. Never restart the lesson, never lose progress. |
| **Hindi string overflows a button** | Fix the layout, never the translation. Truncating Hindi to fit an English-sized button is how the app tells a Hindi learner they are an afterthought. |
| **Parent locale ≠ learner locale** | Legal and expected (D16). The weekly summary uses the **parent's** locale; the learner's screens use the learner's. |
